# 设计决策（v1.0）

README 记录"做到了什么"，`docs/api.md` 记录"怎么用"，本文记录**为什么这么做**
以及**哪些方案被否决了**。所有数字都来自仓库里的基准脚本，口径见
`docs/baseline.md`；跨会话绝对值会漂，引用时带日期与场景大小。

## 1. 定位与边界

Quarry 的目标不是再写一个渲染器，也不是追平 Embree 的绝对速度，而是回答三类
空间查询，并把**构建、查询、更新**都留在 GPU 上：

- 三角形：射线求交、closest、kNN、半径；
- 点云：closest、kNN、半径；
- 高斯：到椭球实体的 closest、kNN、半径。

三者在同一棵 BVH、同一套遍历骨架上实现，只有"叶子里测什么"不同。这个统一接口
加上增量更新，是相对 Embree / Warp / cuBQL 的差异点；绝对吞吐不是。

不做：渲染与着色、多卡 / 分布式、极小场景（< 10 万图元）的绝对倍数、光线 packet。

## 2. 为什么是 BVH

均匀网格和八叉树都试过方向性论证，最后选 BVH：

- 三角形与高斯在空间上的尺寸差异很大，均匀网格会被大图元拖成"每个格子都命中"；
- 八叉树适合点，但对三角形需要图元复制，射线遍历时兄弟节点访问不连续；
- BVH 的叶子可以换载荷（三角形 / 点 / 椭球），这直接换来"一套查询服务三种图元"。

树形用隐式布局而不是指针树：节点数组连续，父盒由两个子盒逐位合并，refit 与
校验都可以按层并行。

## 3. 默认 LBVH，SAH 作为显式选项

**LBVH**（Morton + 基数排序 + Karras 二分）是默认路径：

- 2M 三角形整树构建 7.4 ms（2026-10-30，同会话）；
- 对 Embree 32T 构建打平到领先 3–5×（8k 持平、131k 3.3×、2M 4.9×）；
- 对 cuBQL 默认构建器 2×、对其 SAH 14×，对 Warp 60–80×（2026-10-31，2M）。

**SAH**（自顶向下、16 箱 × 3 轴，Wald 2007）作为 `--sah` / `builder="sah"`：

- 树深 31 → 23，每查询节点测试 477 → 363（2M 地形）；
- closest 1.27–1.45×、kNN 1.45×、高斯 1.40×；
- 代价是构建慢 2.5–3.1×（2M 62.2 ms），随机三角形汤 0.91×（负收益）。

所以库不替用户猜：默认 LBVH，SAH 由调用方按场景选择。SAH 内部还有两条实现选择：
区间 ≤64 图元退回对象中位数 + 串行建子树；选切分用后缀盒代替 O(箱²) 扫描，分区
复用左右标记，把 2M 构建从 74.5 压到 62.2 ms。分箱仍占 52%，是下一个构建目标。

**8 箱实验被否决**：构建持平，高斯查询反而 −6.5%，已回退。

## 4. 节点布局与编号

`GpuBVHNode` 是 32 字节（6 个 float + 2 个 int）：

- 一个 128 B 缓存事务正好装两个节点；
- 内部节点 `0 .. n-2`，叶子固定 `n-1 .. 2n-2`，叶子编号由槽位唯一确定；
- 叶子用 `left = -(slot + 1)` 编码（`left < 0`），`right` 存图元个数（LBVH 恒为 1）；
- `primIds[slot]` 记录槽位对应的**场景索引**，所有查询结果对外报场景索引。

固定叶子编号带来一个关键简化：树的结构变化时，只需重新分配内部节点与槽位，
查询侧永远只认"槽内引用"，不需要在遍历中查场景映射表。拓扑更新后槽序可以
与场景序完全不同，查询结果仍然正确——这是第 9 节"不引入稳定槽位"的前提。

## 5. 三种图元共用一套骨架

GPU 上没有虚函数。三种叶子载荷用模板 traits 区分：

| traits | 叶子载荷 | 叶子距离 |
|---|---|---|
| `TriOps` | `Tri` | 点到三角形最近点的平方距离 |
| `PointOps` | `Vec3` | 两点平方距离（盒退化成单点） |
| `GaussianOps` | `Gaussian` | 点到椭球实体的平方距离 |

遍历、栈、剪枝、结果打包、refit、校验全部复用。高斯的叶子盒是椭球的**外接盒**，
末尾按坐标量级补余量——盒是剪枝下界，短一个 ulp 就可能漏掉真正更近的图元。

椭球距离是本项目唯一新增的数值内核：查询点在内返回 0，在外解 Eberly 方程
`F(t) = Σ (a_i y_i / (t + a_i²))² − 1`。求根固定 14 轮，括号
`[0, 2·a_max·|y|]` 两端符号有保证，牛顿步只在括号内采用，否则二分。**不提前退出**，
因为 CPU/GPU 必须走同一串运算；与 float64 参考的最差相对误差 1.7e-7。

不做密度 / Mahalanobis / 屏幕投影：查询层回答的是几何，不是渲染语义。

## 6. 遍历

- 每线程显式 DFS 栈（二叉 64、宽节点 128），近孩子后压先出，先收紧最优再剪远支；
- 剪枝用"下界 `<=` 当前最优"，不是 `<`：距离并列时还要比较场景索引，等号情形
  可能藏着并列但索引更小的解；
- closest 与 kNN 的并列规则都是 `(dist2, 场景索引)`，CPU 的 `closerHit` 是唯一尺子；
- kNN 每线程维护定长 32 项有序表，第 k 近同时是剪枝阈值；k > 32 在主机侧报错；
- radius 走"计数 → 前缀和 → 填充 → 分段排序"两遍遍历，输出 CSR，结果条数不设上限；
- 射线用 slab 测试，`tMax` 剪枝留 1e-6 余量：盒入口与三角形 t 由不同表达式算出，
  差几个 ulp 时不能把真实命中挡在门外。

## 7. 查询调度与宽节点

**Morton 排序**（`RayOrder` / `QueryOrder`）让同一 warp 访问同一块树：

- 2M closest 100k 1.67×、200k 1.89×，kNN 1.46×，随机汤 1.80×；
- 20k 查询无收益（并发不足以形成访问局部性），radius 几乎无收益，高斯小批次倒退；
- 所以默认 `Input`，阈值交给调用方，不设全局启发式。

**BVH4 宽节点**把偶数深度内部节点折叠成 128 B 节点（孩子 + 孙子四槽）：

- 2M 未排序射线 1.72×、closest 1.69×、kNN 1.42×；
- 射线已按 Morton 排序后只剩 1.01×（相干访问已经把取数压到最低）；
- 与排序叠加时 closest 端到端 1.86×，是目前 2M 的最好数字。

两点必须说清：折叠不改树，只改读取粒度；这是单射线 / 单查询路径，没有 SIMD
packet，因此不能据此宣称追平 Embree。

## 8. 增量更新：refit

refit 的合同是**拓扑冻结**：第 i 个图元还是建树时那个图元，数量与顺序不变。
它只重算叶子盒并自底向上合并，所以结果仍然逐位精确，但盒子会随位移变松。

- 全量路径重传整份图元并重排进叶序；
- 局部路径只上传 `dirty` 的场景索引，沿 `parent` 链用 epoch 标记脏祖先，逐层只
  合并被标记的节点；耗时随"改动量 × 树高"走，不再与场景大小成正比；
- 有宽节点层时，末尾重发受影响的宽节点；refit 之后宽节点里的盒已过期，调用方必须
  重新折叠（C++ 侧合同，Python 目前只走二叉路径）；
- 设备内存池复用临时块与宽节点容量，2M 稳态更新降到整树重建的 0.12–0.27×。

数字：2M 1% 局部 refit 1.0–1.9 ms（LBVH / SAH），131k 0.49–0.66 ms。点云的全量
refit 反而比重建快（Morton + 排序比上传更贵），三角形 2M 则相反。

**叶子批量被否决**：每叶 4–8 个图元让射线慢 2.2×、kNN 慢 1.76×，构建只快 1.54×，
根因是 Warp 的差距来自 SAH 树形，不是叶宽。该实验已回退。

## 9. 拓扑更新：为什么可以不要稳定槽位

图元数量变化后叶子编号 `n-1+slot` 全部失效，必须重编号。当前做法：

1. **切分选择**：从被删除的叶子沿父链上溯，得到一组覆盖改动、每棵 ≤ T 叶的
   antichain（切分根）；
2. **森林 SAH**：只重建这些子树；改动太散 / 太深 / 占比过大时回退整棵重建；
3. **规范重编号**：内部节点按 `(深度, 源序)` 排，叶子 = `n-1+slot`；
4. **槽序**：旧槽序压缩掉被删的，后面接新增图元（先 `inserted` 后 `appended`），
   保证每个子树覆盖的槽区间仍然连续；
5. **场景序**：由 `primIds` 单独记录。幸存者的新场景下标用位移表
   `shifts[j] = inserted[j] - j`（非降）二分求出。

**不引入稳定槽位**是这里最重要的取舍。查询只读"槽内引用"与 `primIds`，槽序不必
跟随场景序；新图元统一接在槽尾，中间插入不需要挪任何旧槽。代价是 `primIds` 一般
不再是 `iota`，但这个代价只落在一次 O(n) 的映射上，不进入遍历。

盒子只重算脏节点：森林里的全部内部节点，加上切分根与移动叶子在新树里的祖先；
没被碰过的旧内部节点直接沿用旧盒。

回退条件：删除 + 新增超过旧数量的一半、重建叶数超预算、切分根过散、深度超过
`topoBaseDepth + 6`、`n < 2`。深度上限用来兜住质量漂移：连续同向追加会让某条
路径逐轮变深，5 轮 1% 中插后节点测试约 1.1× → 1.7× 同场景新鲜树，超过基深度
6 层就整树重建重新平衡。"升一级切分"（累计重建叶数 / 切分块增长）仍未做。

已知代价：规划、载荷重排与整块重编号都是 O(n)。2M 只删 3.4 ms，中插 / 尾插
11–12 ms，`relayout` 占更新总时间的一半左右；内存池让稳态更新降到整树重建的
0.12–0.27×（中插 0.20–0.32×）。下一步若要再压，只能动 O(n) 重编号本身
（稳定槽位 / 原子编号 / 稀疏叶子重发），那是另一轮设计。

## 10. 可复现正确性

项目的"正确"不是"结果差不多"，而是**逐位相同**：

- 所有几何是 float32；CPU 与 CUDA 共用 `core/geometry.h`，同一串运算顺序；
- 乘加显式走 `QUARRY_FMA`，nvcc 用 `--fmad=false`，MSVC 不会被收紧成 FMA；
- 高斯求根固定 14 轮、无提前退出；并列规则唯一；
- 同一输入 → 同一棵树（`treeHashGPU`）→ 同一批结果（FNV 指纹）。

验证链：`selftest` 43 项；Python numpy 对拍 84 项；`validate*` 检查父盒逐位等于
子盒之并、叶子盒等于图元盒、每个非根节点恰被引用一次；外部对照（Embree / Warp /
cuBQL）比命中数与 t 值。

## 11. 测量方法

- GPU 查询时间用 CUDA events，只包 kernel；构建与 refit 报墙钟（调用方真实等待）；
- 进程内第一次启动 kernel 会付 CUDA 模块懒加载，计时前先空跑一次丢弃；
- 绝对值受笔记本 DVFS / 散热影响，跨会话可差 1.3–2.5×——只认同会话成对比较；
- 场景大小、射线相干性、是否含排序、测量日期，四个口径缺一不可；
- 质量漂移必须用**同轮**新鲜构建做对照：脚本本身在改场景，拿旧跑分当分母会骗人；
- 判断"自己的改动变慢"之前先做三组对照（只删 / 只插 / 混合），分清既有路径的慢
  与新引入的慢。

这些教训来自实际踩坑：Warp 重心坐标约定写错导致 96% 的点距离偏大；构建计时混入
模块加载；宽节点实验在排序之后收益归零。

## 12. 被否决 / 未做

| 方案 | 结论 |
|---|---|
| 每叶 4–8 图元（Morton 批量） | 射线 2.2× 慢、kNN 1.76× 慢，已回退 |
| 8 箱 SAH | 构建持平、高斯 −6.5%，已回退 |
| 内联子节点包围盒（64 B 节点） | 实测负收益，已回退 |
| 稳定槽位 | 查询不需要，见第 9 节 |
| 宽节点用于已排序射线 | ≈1.0×，无收益 |
| 点云全量 refit 代替重建 | 点云上全量 refit 反而更快，保留 |
| BVH8 / SIMD packet / 非相干射线两遍排序 | 未做 |
| 每叶 4 图元的 SAH 形态 | 未做，是构建侧下一个杠杆 |

## 13. 下一步

1. **构建**：每叶 4 图元 + SAH 分箱降本，缩小与 Warp 的构建差；
2. **拓扑**：把 O(n) 的 relayout 压到带宽量级（稳定槽位 / 原子编号 / 稀疏重发），
   并给质量漂移加主动判据；
3. **查询**：非相干射线两遍排序、packet 路径（明确不承诺追平 Embree）；
4. **交付**：旗舰用例（一个真实的动态场景 demo）与更多非均匀模型（Dragon / Lucy）。
